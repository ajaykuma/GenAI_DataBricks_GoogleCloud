#### Comparing D-2.0.2 / D-2.0.3-0 / D-2.1 / D-2.2

All four scripts build the same LangGraph pipeline (basic description → features/benefits →
3 parallel marketing messages → polished final description) in Streamlit. What changes between
them is **how the LLM is called** and **how "memory" is implemented**. None of them do any
LLM *evaluation* yet — that's the gap which is fixed by monitoring implmentation.

### 1. Quick comparison table

| | D-2.0.2 | D-2.0.3-0 | D-2.1 | D-2.2 |
|---|---|---|---|---|
| LLM call style | `llm.generate([messages])` (batch API) | `llm.generate([messages])` (batch API) | `llm(messages)` — deprecated "call the object" style | `chat_llm.invoke([...])` (current API) + raw `AzureOpenAI` client for one node |
| Memory lives in | Graph `State["history"]` (Annotated, but see bug below) | Graph `State["history"]` + per-node skip logic | External module-level dict `SESSION_HISTORIES[session_id]`, decoupled from graph `State` | `st.session_state.PRODUCT_MEMORY` — a whole-result cache outside the graph |
| Token usage tracked? | No — `usage` dict is always `None`/0, `accumulate_usage` sums nothing real | Yes — pulls `response.llm_output["token_usage"]`, falls back to word-count estimate if missing | No | No |
| Caching granularity | None (every click re-runs everything; only a request counter) | **Per-field**: each of the 6 outputs is skipped individually if already present, `run_count` and full run history kept | None (only toggles whether the *features* node uses conversational memory or not) | **Whole-result**: if `product_name` was seen before, the entire graph is skipped and the cached dict is returned |
| Session state hygiene | Uses plain **module-level globals** (`PRODUCT_COUNTER`, `RECENT_PRODUCTS`) | Uses `st.session_state` correctly | Uses a plain module-level dict, cleared manually with `.clear()` on every "Generate" click | Uses `st.session_state` correctly |
| Notable bug/smell | Module-level globals are shared across **all** users of the Streamlit app (not per-session) → cross-user leakage in a real deployment. Also `Annotated[List[BaseMessage], "append"]` — the second arg to `Annotated` needs to be a reducer *function* for LangGraph to actually merge parallel branch updates; a bare string `"append"` does nothing, so parallel writes to `history` from the 3 marketing nodes can silently overwrite each other. | Same `Annotated` non-reducer pattern isn't present (history isn't `Annotated` here, it's `List[BaseMessage]`), but since node functions mutate `state["history"]` in place *and* return partial dicts, behavior under LangGraph's parallel branches is still fragile — the 3 marketing nodes each append to the same list object without a merge strategy. | `llm(messages)` calling the model instance directly (`__call__`) is deprecated in modern LangChain — should be `llm.invoke(messages)`. `SESSION_HISTORIES.clear()` on every click means memory never actually persists *across* Streamlit reruns; it only exists *within* one run of the graph. So despite the elaborate session dict, it behaves like no cross-run memory at all. | Cache is on `product_name` only — two different calls for the same product always return the identical cached object, so `use_memory` here really means "answer from cache," not "give the model conversational context." |
| Best-designed piece | — | Real token accounting + deep-copied per-run history is the most complete memory model of the four | Clean separation of "with memory" vs "without memory" nodes for an A/B comparison | Simplest, most readable code; correct use of `.invoke()` |

### 2. The conceptual arc across the 4 files

1. **D-2.0.2** — first pass: put a `history` list and a `usage` dict into the graph `State`,
   call the LLM with `.generate()`, and stitch it into every node. Session bookkeeping
   (counters, recent-products list) is done with bare Python globals — works in a single-user
   demo, breaks in a real multi-user deployment.
2. **D-2.0.3-0** — fixes the state-hygiene bug (`st.session_state` instead of globals), makes
   token usage real (with a graceful fallback), and adds *per-field* memory: each node checks
   "do I already have this piece of the state?" before calling the LLM again. This is the
   most feature-complete version.
3. **D-2.1** — a *different* branch of the idea: instead of storing memory inside the LangGraph
   `State`, it moves memory into a session-keyed dict that lives entirely outside the graph, and
   adds a toggle so you can compare a node running "with memory" vs "without memory" (calling
   the raw Azure client, no LangChain wrapper at all). Useful for validating the *difference*
   between graph state and conversational memory, but the `.clear()` call means memory doesn't
   actually survive between button clicks.
4. **D-2.2** — simplifies back down: no `history` field in `State` at all, `.invoke()` used
   throughout, and memory becomes a simple "have I generated this product before?" cache keyed
   in `st.session_state`. Trades away conversational context entirely in favor of a clean
   result cache.

### 3. What's missing from all four 

None of the four scripts capture anything from `LLM_evaluation_n_metrics.txt` in documentation:
latency, hallucination/faithfulness signals, bias/toxicity flags, reference-based scores
(BLEU/ROUGE), or an LLM-as-Judge pass. 
Adding a monitoring layer that can be dropped into any of these `call_llm`/node functions to start collecting that data without having to rewrite the graphs.
